# Moj Prop: independent MariaDB restore gate (operator-only, not a release authorization)

**Current state:** source-only. No production database dump, independent restore
rehearsal, wallet collection, deployment or real customer purchase is claimed.

## Why two separate identifiers exist

- `restore_case_id` is a numeric 1–20 digit **pre-approved, independently
  reviewed** restore case. It is selected *before* any workflow dispatch, and
  corresponds to the private signed restore receipt.
- `GITHUB_RUN_ID` is generated by GitHub **after** workflow dispatch. It binds
  the backup of application source files and the rollback, not the prior
  independent database restore proof.
- The signed restore receipt must bind the exact **40-hex source commit**,
  independently selected case ID, connected live DB identity SHA256, backup
  SHA256, nonproduction restore name, schema/row checks and a recent (within
  24 hours) timezone-aware timestamp.

## Required evidence (private owner-controlled host only)

1. Identify the *actual* production MariaDB connection through the existing
   Django runtime; the read-only identity helper executes `SELECT DATABASE()`,
   checks the MySQL/MariaDB backend, and hashes engine/name/host/port/user.
   The output is a SHA256 fingerprint, **not database credentials**.
2. Separately create a **full** database snapshot from the authorized MariaDB
   instance and preserve it as gzip, private permissions 0600. Do not place
   customer data, backups, HMAC keys, connection strings or signed receipts
   in GitHub, a public folder, application assets or an Actions artifact.
3. Independently restore that exact snapshot to an **isolated nonproduction**
   database and verify schema and representative row reconciliation without
   modifying production. An operator/reviewer who really performed and
   observed the restore signs the canonical JSON payload using a separately
   provided 32+ byte reviewer key. **A synthetic test never qualifies.**
4. In the private location
   `/home/zomorod2/.mojprop-private-db-restore-evidence/<restore_case_id>/`
   retain only `full-database.sql.gz` and
   `isolated-restore-evidence.json` with owner-only permissions.
5. Provision `MOJPROP_INDEPENDENT_RESTORE_VERIFIER_KEY` (private; never log
   or commit), and `MOJPROP_PRIVATE_DB_RESTORE_ROOT` with the exact private
   path above on the authorized host runtime. No value is provisioned by
   source control or this PR.
6. Only after **separate owner permission** for the reviewed release SHA,
   select the prepared case using manual workflow input
   `restore_case_id`. The workflow rejects nonnumeric case IDs before SSH,
   then checks the actual connected MariaDB identity against the signed
   proof **before changing even the static Moj Prop catalog**. The backend
   installer checks a second time before changing source or migrations.

## Explicit non-claims and abort conditions

This gate rejects expired, corrupted, incorrectly scoped, world-readable or
forged evidence, wrong case/commit/DB identity, missing reviewer key, and
SQLite/unknown connected DB engines. It does not itself generate a snapshot,
run a rehearsal, verify an external reviewer was truthful, guarantee a
database restore on production, attest web routing, or permit charging
customers. Separate **application/media backup and rollback, transaction
safety, Passenger and tenant isolation, release authorization, legal TRON
receiver verification and live order/fulfillment checks** remain mandatory.

On any missing evidence or runtime mismatch, the process **must stop closed**.
Do not set a variable to `true` merely to satisfy a gate. A database
schema migration cannot be reversed by restoring Python files; maintain a
verified database rollback plan and a controlled maintenance window.
