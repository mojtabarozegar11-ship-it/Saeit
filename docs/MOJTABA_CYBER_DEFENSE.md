# Mojtaba.bot.ai — defensive incident response (draft)

This module **does not mean that production protection is enabled**. It adds a
side-effect-free defensive triage and evidence-record implementation for the
Saeit master agent. Integration with authorized application telemetry, external
log retention, incident notifications, approvals, and backup infrastructure is
a separate deployment task.

## Single-robot identity

The only authorized *top-level* product identity is **Mojtaba.bot.ai**,
with stable identifier `mojtaba.bot.ai`. The former public shorthand
`Mojtaba.bot` resolves to this same identity; it does not create a second bot.
Research, trading, security, factory and other specialist agents are internal
components. `core.bot_identity` validates proposed top-level registries but
does not migrate, disable, delete, or merge any live workers or database rows.

## Design and operating controls

1. **Ingest:** `core.cyber_defense.make_security_event` accepts only fixed
   event types, metadata identifiers, valid IP addresses, and safe numeric/
   boolean indicators. Never ingest message bodies, personal documents,
   passwords, tokens, API keys, or customer records into security logs.
2. **Triage:** `triage_security_events` detects authentication bursts,
   suspicious transfer patterns, and account/integrity anomalies. A finding
   is a *signal*, not proof of theft, malware, or offender identity.
3. **Evidence:** `seal_evidence` chains SHA-256 hashes; `verify_evidence_chain`
   detects modifications or missing records. For admissible custody, save
   records independently in append-only, access-controlled, off-host storage
   with trusted time, retention limits, and documented custodians. A hash
   chain generated by a compromised system is not independent proof.
4. **Attribution:** `identity_assessment` distinguishes unknown actors,
   unverified technical leads, and corroborated cases requiring authorized
   review. Never publish a person's name based solely on IP/account/device
   evidence. Preserve privacy and allow forensic review.
5. **Containment and recovery:** `defensive_response_plan` proposes, but
   **never automatically executes**, account/session revocation, credential
   rotation, isolating owned assets, inspecting verified clean backups,
   notifications, and preparing provider preservation/takedown requests.
6. **Stolen data:** Rebuild owned systems from verified backups; use legal
   providers and lawful process to request return/deletion of any stolen copy.
   Do not claim remote deletion is technically verifiable or guaranteed.
   Unauthorized intrusion into another person's systems is prohibited.
7. **Agent trust boundary:** Treat retrieved pages, email, logs, and tool
   outputs as untrusted data. A model suggestion can never grant privileged
   access, approve a payment, deploy code, or authorize a destructive action.

## Required release gates

- Identify actual live Mojtaba.bot.ai deployment and its explicit scope of assets.
- Integrate authenticated telemetry and immutable external evidence storage;
  verify detection sensitivity, false positives, audit access and retention.
- Verify offline/off-host backups and restore on an isolated owned system.
- Obtain case-specific owner approval before production changes, provider
  correspondence, notification, payment, credential rotation or deploy.
- Validate data-protection and incident-reporting obligations with appropriate
  local counsel, and retain a human emergency stop for unsafe automation.

Run standalone tests with `python -m unittest core.test_cyber_defense -v`.
